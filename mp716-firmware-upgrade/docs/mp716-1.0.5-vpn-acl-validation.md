## WLAN 探针准备、失败处理与成功关联

首次 fresh scan 返回 Windows `ERROR_BUSY`（170）。这次尝试没有添加任何路由器 ACL，自动清理确认原 WLAN、原 profile 集和有线接口保留、临时 profile 删除。

随后只在本地修正探针的扫描处理：

- 使用合法的 NULL SSID 常规可用网络扫描，监听实际完成事件。
- 仅对 170 等待已有扫描结束并短暂退避，总预算 55 秒、最多 10 次扫描请求。
- 权限错误、其他错误、已接受扫描的失败/超时和用户停止不会被当成 busy 无限重试。
- 首次扫描完成后才添加临时 profile，避免紧接自身 profile 变更请求扫描；既有 busy 的根因没有被强行归因于此。
- 原失败 trace 保留，每次新运行写唯一文件；不记录密码或完整 profile XML。

本地扫描编排的 8 项模拟测试通过，不调用 WLAN DLL/网卡或设备。随后由主执行者运行的新探针，在一次连接尝试内成功完成扫描、目标 AP 关联和 DHCP 地址获取。成功证据为 `wlan-probe-connect-20261119-142411-64ee405c.private.json`；该次 trace 记为 `CONNECTED`，观察到的连接尝试编号只有 `1`。

此处不宣称 Windows 所有扫描或关联问题都已解决；通过的是本轮有界探针的实际连接路径。

## 终端 ACL 实际数据面结果

所有阶段均将 Wi-Fi 与有线探测 socket 绑定各自接口及源地址；有线控制始终使用独立 Ethernet ifIndex 9。三阶段验证同一个 Wi-Fi MAC、同一个 Wi-Fi 地址和同一个外网目的 IPv4，报告中仅公开“相同”的核验结果，不公开地址。

| 阶段 | 操作及实际观测 | 结果 |
| --- | --- | --- |
| Before | 添加规则前，Wi-Fi 管理 HTTP、路由器 DNS、同一外网目标 HTTP 均成功；同目标有线 HTTP 在 Wi-Fi 测试前后成功。 | PASS |
| Add | 从有线控制连接 POST `hosts/device-acl`，只添加已识别的受控 Wi-Fi MAC；核验原生列表保存成功、nft `blocked` 集合包含该 MAC。添加后计数基线为 0。 | PASS |
| Blocked | Wi-Fi 到固定外网目标的 3 个新 TCP 连接均超时；同期同目标有线访问前后成功。原生测试会话读取到 nft 丢弃计数 `0 → 9`。 | PASS |
| Blocked 本机访问 | 被限制 Wi-Fi 仍可访问路由器管理 HTTP 和路由器 DNS，符合规则只在 forward 链阻断转发的设计。 | PASS |
| Remove | 从有线连接 POST 原生移除操作，只删除本次受控 MAC，确认 ACL 列表和 nft 集合恢复原值。 | PASS |
| After | 保持上述同一 Wi-Fi 身份和同一外网目标，新 HTTP 连接恢复；管理 HTTP、DNS 及有线同目标访问均成功。 | PASS |

主要证据：

| 本地文件 | 支持的断言 |
| --- | --- |
| `native-acl-session.json` | `native_acl_saved`、`nft_set_applied`、实际计数增长、规则移除、`traffic_test_complete=true`、原 ACL 集合恢复、退出时无本次受控条目；`browser_clicks_tested=false` |
| `wlan-probe-before.json` | `passed=true`，原流量可达，接口绑定及有线控制可用 |
| `wlan-probe-blocked.json` | `passed=true`，3 次新 Wi-Fi TCP 均 `TimeoutError`，有线对同目标前后成功，管理/DNS可达 |
| `wlan-probe-after.json` | `passed=true`，移除后同一身份及目的地址转发恢复 |

丢包计数以原生 ACL 会话的 `BLOCK_PROVEN` 时刻读取为准。添加/移除规则会重建表并重置计数，不能要求后续恢复快照仍保留同一个累计数。真实转发测试与计数增长共同构成阻断证据；单独保存 MAC 或返回成功不作为数据面通过依据。

## VPN P1 的源码修复状态

冻结的 1.0.5 设备镜像仍包含前轮发现的 `jsonfilter -e "@$1"` 错误。源码工作区已修正对象属性选择器，并加入服务计划读取/类型验证与错误处理，防止解析失败被当成关闭状态后删除 guard 或改变凭据绑定。修复涉及 `integration/ram-web/mp716-vpn.init` 与配套测试，**尚未安装到正在运行的设备**。

最终真实解析器回归共 **18 项通过、0 项跳过，耗时 111.798 秒**，包含全部 8 字段、合法禁用、旧/新文件损坏、读取及查询失败、错误类型、NUL/换行及异常不改 guard/CHAP 等情形。临时副本将选择器改回旧的 `@$1` 后，正向启用用例确实捕获语法错误，证明本次回归可以检出原缺陷。

新增 `scripts/build-jsonfilter-host.py` 从固定提交及 SHA256 校验的官方源构建真实主机解析器。GitHub 原生后台检查、固件构建和 Gitea 固件构建的主机测试均已接入；严格模式缺解析器会失败，不再将假解析器或整组跳过当作回归通过。三个 workflow 的 actionlint、Python 语法及 VPN init Shell 语法检查通过。本轮没有推送或触发这些工作流。

本机实跑固定 jsonfilter 源码及 Windows json-c 0.18；Linux bootstrap 尚未在 Linux 实际编译，Ubuntu CI 使用并记录系统 json-c 0.17。测试直接调用带副作用桩的 `start_service`，未覆盖实际 `rc.common`/procd 的 reload 返回码和旧实例保留行为，也未验证真实隧道互通。这些边界不能由主机测试成功替代。

本轮没有启用原本关闭的 VPN，也没有为验证修复而重启相关服务或刷新固件。已运行 1.0.5 的 VPN P1 仍需后续构建、验签及明确授权部署后，才可做真实启动、规则就绪和远端互通验收。
